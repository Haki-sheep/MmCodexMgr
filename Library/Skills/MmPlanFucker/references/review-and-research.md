# 设计审查与调研

用于完善已有设计、引用同类游戏或评估实现方案。只选与当前设计有关的检查项，不把检查目录作为每次回答模板。

## 设计审查

从玩家实际行为和规则状态推演，优先找会让功能无法闭合或体验目标落空的问题。

| 检查面 | 要核对的内容 |
| --- | --- |
| 体验目标 | 实际奖励的行为是否符合期望体验 玩家是否有可感知的选择和反馈 |
| 规则闭合 | 入口 前置条件 输入 状态转移 结果 失败 中断和退出是否能连成具体操作过程 |
| 决策价值 | 是否存在无代价最优解 无意义等待 重复操作或与目标冲突的激励 |
| UI 与逻辑 | 可见可点条件与执行条件是否一致 操作后能否判断成功 原因和下一步 |
| 数据与数值 | 单位 作用范围 上下限 舍入 同时发生的顺序及资源增减是否一致 |
| 模块边界 | 谁拥有规则和状态 谁提供数据 谁发起操作 是否存在循环依赖或重复扣除 |
| 内容产能 | 是否依赖大量独特关卡 动画 文案 资产和人工配置 是否符合团队能力 |
| 开发约束 | 平台 输入方式 引擎/框架 现有系统及性能目标是否对设计构成限制 |

只讨论实际会发生或由本案规则推导的边界。例如本地单人功能不无依据添加联网重试或服务器方案。

每个重要发现使用可追踪信息：

- 定位：对应模块、规则编号或原文
- 性质：规则矛盾 / 关键缺失 / 体验风险 / 待实测假设
- 场景：什么输入和状态触发问题
- 影响：玩家、其他模块或制作成本会怎样变化
- 建议：推荐修订；仅有实质取舍时补一个备选
- 决策：能在既定意图下补齐，还是需要用户选择

优先处理阻断规则成立的问题，再处理体验和实现风险。不用虚假的总分替代论证。

## 同类游戏调研

调研围绕当前要解决的机制或体验问题，一般挑最贴合的一至两个参照；不要因美术或类型相近就当作同机制。

1. 明确要核对的具体行为，如失败后保留哪些资源、背包满时如何拾取、技能打断是否消耗冷却。
2. 实际打开可访问来源。优先游戏官方说明、开发日志、开发者演讲、更新公告；可用实机演示补充可见行为，标出时间点和能观察到的范围。
3. 输出“观察到的机制 → 对本案的启发 → 不适用之处”，把来源事实与策划推断分开。
4. 在相关结论旁给直接链接。记录能确认的平台、版本或来源日期；无法确认就说明未知。
5. 不从画面表现推断内部架构、算法或后台数据。不可访问的来源不能作为已核实证据，不用 AI 生成画面补充实机证据。

来源相互冲突时比较版本与平台，保留冲突，不能挑方便的说法直接定案。无法联网时可先完成内部规则审查，竞品部分明确待核实。

## 技术选型与实现难度

先区分实现难度与内容工作量。设计简单不代表资产、关卡和调参成本低。

- 已有项目：沿用当前技术栈和公开接口，检查相关代码/资源后说明可复用部分与缺口。不要从本 Skill 所在机器或上一个项目推断引擎与架构。
- 新项目：只有平台、2D/3D、联网方式或团队技能会影响结果时才补问。最多给两个实现路径并明确推荐，不堆框架列表。
- 难度按低/中/高给出依据：规则与状态复杂度、跨模块依赖、表现/资产成本、性能/联网约束、验证成本。仅列相关维度。
- 工期估算需有团队投入、熟练度、资产可复用情况和交付质量假设。缺少依据时给工作拆分与不确定项；用户需要粗估时给带前提的区间，不报无依据的精确天数。
- 对最大风险提出最小验证，例如少量敌人的手感原型、一个界面的操作验证、实际设备上的性能采样。注明预期判断标准，未执行时称“验证计划”。
- MVP 保留验证核心体验所需闭环，明确后续可扩展内容。删减机制应说明体验损失，不能只依据程序实现成本。

技术结论放在对应模块的实现备注中。玩法正文描述规则，不用类名、框架名和数据存储细节挤占玩家体验说明。
