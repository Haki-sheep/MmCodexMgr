# 逻辑与 UI 成稿约定

按用户既有格式裁剪以下结构。小功能只保留必要内容；模块之间划清责任，同一规则只保留一个详细权威位置。

## 文档组织

- 全案开头：当前范围、体验目标、已确认约束、草案或定案状态、仍影响结果的待决项
- 每个功能模块：职责与非职责、规则与操作过程、UI 交互与状态、外部 `@引用`、验收条件；UI 配图仅在用户要求时加入
- 只在有需要时补充数值表、资产需求、技术风险和最小验证计划

规则编号在当前模块内稳定，如 R01；UI 控件编号如 U01；验收编号如 A01。调整文字不随意重排既有编号。多个模块可使用相同局部编号，跨模块定位时带模块名。

## 单模块表达

| 内容 | 需要讲清楚 |
| --- | --- |
| 目的和职责 | 玩家为什么使用 谁维护规则与状态 哪些内容属于其他模块 |
| 入口和条件 | 从哪里进入 在什么状态能操作 所需资源和限制 |
| 逻辑规则 | 输入 前置条件 状态变化 资源变化 结果 顺序及有意义的失败分支 |
| UI 示意（用户要求时） | 实际可查看的线框图 界面示意或可交互原型 配合控件编号 |
| UI 状态 | 显示内容 可见/可点条件 交互反馈 空态或失败原因 与规则的对应关系 |
| 外部关联 | 发生关联的位置写 @目标 说明读取 请求 通知等关系 |
| 验收条件 | 给定状态和输入 观察到的规则结果与 UI 表现 |

先用一条具体操作串起来，再补必要分支。每个能触发业务的控件都应能定位到规则；每个需要玩家感知的规则结果都应有反馈位置。没有 UI 的纯规则模块不强行添加界面。

## @引用与耦合契约

`@` 是可定位的依赖标记，不代表代码中必须直接互相引用。不因使用 `@` 就额外引入事件总线或其他框架。

- 模块级：`@背包`
- 具体规则级：`@背包.接收物品`
- 如果用户已有 `@xxxx` 名称，直接沿用
- 文档格式允许时将该文字链接到实际章节或文件；不支持链接时提供精确标题和位置
- 未定义的目标明确标记“待定义”，列出所需契约，不伪造完整接口
- 在调用位置保留引用，完整契约只在所属模块写一次；其他位置链接过去

需要描述的契约按实际关系取舍：

| 项 | 内容 |
| --- | --- |
| 归属 | 规则和最终状态由哪个模块负责 |
| 发起方与目标 | 谁在什么业务时机读取或请求 @谁 |
| 输入 | 必需的业务数据及其语义和单位 |
| 结果 | 成功和拒绝的业务含义 需要返回的信息 |
| 副作用 | 哪些状态或资源发生变化 由谁改变 |
| 表现责任 | 哪个界面显示结果 谁提供可显示信息 |

例如：这是说明契约写法的独立示例，不是所有项目的固定规则。

> 掉落模块 R02：玩家拾取时请求 `@背包.接收物品`，传入物品类型与数量。背包拥有容量检查与入库规则，返回实际接收数量；掉落模块据此扣减场景剩余数量。全部接收后移除掉落物，零接收时保持掉落物并由拾取提示显示拒绝原因。是否允许部分接收必须在当前设计中明确决定。

如果发现互相等待、双方都扣资源或双方都以对方为状态权威，先指出冲突并明确归属。不要仅补两个 `@` 标记就称为解决了耦合。

## 图文结合

默认以文字、控件说明和状态表表达 UI。仅在用户明确要求时制作 UI 概念图、草图、线框图或可视原型；未要求配图时省略图片章节和占位，不影响策划案完整性。

用户要求配图后，将 UI 图与对应规则放在同一模块附近，图注说明页面/状态、关键控件编号及示意性质。逻辑和 UI 分段清楚，但通过编号相互对应。

- 线框图用于布局、信息层级、交互和状态验证；它不等于已定稿的视觉风格
- 参考游戏截图必须来自可核对来源，附链接和相关版本信息；无权访问时不能假装已获取
- 概念图用于视觉方向，不承载唯一的精确规则、数值或控件标注
- 精确文字、数值和状态采用可编辑结构，避免只存在于生成图片里
- 用户主动要求流程图时再画；未要求时用操作步骤和状态表说明逻辑

无论是否配图，UI 状态表都可按需使用：

| 控件 | 当前状态/条件 | 展示与交互 | 触发规则 | 结果反馈 |
| --- | --- | --- | --- | --- |
| U01 | 对应具体业务状态 | 可见性 可点性 文案或内容 | R01 或 @目标规则 | 确切变化及反馈位置 |

此表是结构示例，成稿需填本案实际内容，不能保留“对应具体业务状态”等占位文字。有图时核对图和状态表的一致性。

## 交付与变更

采用用户明确指定的格式和位置。未指定格式时默认 Markdown，要求配图时将图片与文档放在同一目录；不要因制作策划案自动发布网站或建立云文档。

允许写文件且用户要求配图或原型时，按当前格式提供真实图片/原型文件及有效链接，优先相对引用以便移动。未要求时只交付 Markdown，不创建空图片目录。返回给用户的本地文件链接用绝对路径。不自动生成多个格式副本，避免出现多个不一致的权威来源。

交付前检查与本次范围有关的内容：

1. 关键流程能从进入走到成功、失败或退出，没有互相矛盾的条件
2. UI 说明、状态表和逻辑规则对应；交付含图时再检查图文一致性和图中文字可读性
3. @目标可定位，状态和副作用有唯一归属；未解决的引用已标明
4. 建议、假设和用户已确认内容有明确区分；示例数值不冒充已平衡数值
5. 关键判断有来源或推理，难度与验证计划未冒充实测结果
6. 本次交付的文件及引用图片实际存在，按交付格式预览可读；未完成预览时如实说明

后续修改从受影响的规则出发，检查同模块 UI 和验收，再沿 `@引用` 找依赖。只修改授权页面，跨出授权范围的影响在对话中说明。
