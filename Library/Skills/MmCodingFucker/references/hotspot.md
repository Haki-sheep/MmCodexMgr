# 热点与维护成本取证

用于范围较大或需要历史支持的债务调查 局部代码已有足够成本证据时不强制执行

## 固定口径

记录仓库根目录 当前分支或提交 调查路径 时间窗口 未提交修改和历史完整性
优先采用用户指定窗口或项目发布周期 未指定时选择与当前维护活动相关的窗口并解释依据
Git 仓库根目录可能高于用户给定目录 必须限制 pathspec 不扫描无关目录
浅克隆 无历史 迁移仓库或 squash 提交会限制解释力 如实报告 不自动拉取历史

区分两个量

- 修改频率 某路径在窗口内被修改的去重提交数
- churn 某路径在窗口内的文本增删行数 二进制的缺失数值不能当零

二者分别报告 不把 churn 当作修改频率 不直接相乘生成债务利息或质量分

## 可复核的数据收集

使用项目已有的 Git 或分析工具 以下 PowerShell 命令中的变量先按实际范围赋值

```powershell
git -C "$RepoPath" rev-parse --show-toplevel
git -C "$RepoPath" rev-parse --is-shallow-repository
git -C "$RepoPath" status --short -- "$ScopePath"
git -C "$RepoPath" log "$Revision" --since="$Since" --until="$Until" --no-merges --format="commit:%H%x09%aI%x09%s" --name-status --find-renames -- "$ScopePath"
git -C "$RepoPath" log "$Revision" --since="$Since" --until="$Until" --no-merges --format="commit:%H" --numstat --find-renames -- "$ScopePath"
```

保留命令与统计口径 no-merges 会排除仅发生在合并提交中的改动 有相关证据时单独检查这些提交
按提交与路径去重 后续程序化解析应使用适合文件名的结构化或 NUL 分隔输出 不按空格猜路径
重命名沿明确映射追踪 无法追踪时注明历史断点 不声称新文件没有历史债务

结合项目约定识别生成物 第三方和构建输出 将纯搬迁 格式化和批量机械更新与语义修改分开
列出排除理由和受影响提交 不悄悄滤掉反例 不能确定性质的提交保留并标记
代码规模只能作为复杂度代理 圈复杂度使用已有分析器的实际输出 不从行数换算
不同语言 工具版本和分析粒度不直接比较复杂度值

## 共同修改

在同一窗口与排除规则下统计 A 的变更提交数 B 的变更提交数 和两者同时修改的提交数
报告原始计数及方向比例 例如 A 改动中有多少次同时改 B B 改动中有多少次同时改 A
样本量小时标明证据弱 不用固定百分比自动判定耦合 不给最少只出现一次的共变高置信度
打开代表性提交核实是否为同一业务变化需同步多个入口 排除提交习惯 批量更新和测试随实现修改等合理原因

成本可能出现在稳定接口的调用方 底层从未修改时不存在可用的共同修改信号
此时沿直接调用或引用关系检查重复适配 规则同步和绕行代码 并用调用方历史验证额外维护步骤
不要仅因接口稳定就推断设计健康 也不要只因调用方多就要求重构接口

## 从线索到条目

热点筛选调查对象 不直接证明债务
对候选定位具体职责或契约 说明一次实际修改怎样传播 哪些步骤属于额外负担
消费已有 issue 修复与回滚记录时 核实缺陷内容及结构根因 不通过主动 Bug 搜索扩展职责
结合已知近期需求判断是否会再次付出成本 未来需求未知就注明 不从历史直接推算工时或收益
证据不足留为候选 缺少历史不阻止使用代码中可验证的修改传播证据
