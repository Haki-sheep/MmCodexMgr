# Unity 逆向还原中的协调与执行经验

本参考来自 Escape from Duckov 还原会话。适用于协调多个执行会话、恢复 Unity 渲染资源、复现视觉错误和整理验收证据。主 Skill 可在涉及这些工作时引用本文件。

下面的案例用于决定下一步怎么做。Unity 版本、场景名、会话别名和路径均须按当前任务核对。单次成功不代表全部场景通过，未知原因保持未知。

## 一 协调者的问题与改进

### 1 查错执行者身份

- 出现的问题 用户问 DSF 小弟的错误，协调者检查了独立 DSH 桌面服务，拿到了与实例 2 四个执行会话无关的服务离线结果
- 为什么出现 把用户别名直接映射成工具中的执行端名称，没有先核对别名对应的实例、会话和实际后端
- 如何解决 记录用户别名与准确实例 ID、会话 ID、工作目录的对应关系。用户已经确认实例 2 的四个会话就是 DSF 时，以该映射为准。前端实例类型不能单独证明模型后端
- 如何加快速度 复用已确认的身份映射和原任务 ID。诊断针对原任务执行一次，避免检查无关服务或创建替代会话

### 2 工具入口与工程版本不匹配

- 出现的问题 Unity 2022.3 工程曾走不兼容的控制入口，直接启动 Editor 又遇到许可证问题。重新打开时，Hub 拒绝带正斜杠的项目路径，换成经系统解析的 Windows 绝对路径才成功
- 为什么出现 把 CLI、Editor、桥接包和启动器当成可以互换的入口，没有先核对各自支持范围和实际运行实例
- 如何解决 先确认工程版本、存活 Editor、桥接能力和当前模式，再选择匹配的入口。本例使用现有 2022.3 Editor 和兼容 Bridge，Hub 负责已验证的启动路径
- 如何加快速度 保存已成功的调用模板，运行前只刷新 PID、实例身份和当前状态。修复已确认的参数错误后复用原入口，减少重复启动和工具切换

### 3 对小改动反复跑整条游戏流程

- 出现的问题 为检查单枚 Shader 或 HUD 形状，多次经过菜单、加载、拾取、战斗和长距离撤离。随机敌人缺席会让战斗测试超时，无法回答当前视觉问题
- 为什么出现 没有把待证明的结论与最短必要验证绑定，沿用了已有的大场景测试入口
- 如何解决 先核对目标资源和引用，再验证编译及实际绑定，最后在目标场景固定机位实拍。转场修复验证真实转场，材质修复验证目标物件，跨场景行为改动再跑完整路线
- 如何加快速度 启动前准备好观察脚本和停止条件，避免生成代码期间错过目标场景。到达后暂停自动移动，复用当前现场进行单因素对照。截图跟随实际加载阶段、动画进度或渲染回调触发。已有证据覆盖且代码未变的部分不重复跑

### 4 检查范围与用户看到的问题位置不一致

- 出现的问题 用户提到部分物体发紫，协调者先扫描零号区，却没有定位到错误。随后用户补充，位置在新手教学关卡中段走廊的地面
- 为什么出现 把当前打开的场景当成问题现场。材质的 Shader 显示 supported、没有已有编译消息，也不能证明目标物体的实际绘制正确
- 如何解决 缺少位置时尽早索取场景或物件描述，同时推进其他独立修复。到目标区域后核对 Renderer、材质槽、Shader、关键字和实际 Pass。后处理应检查真正的游戏渲染相机及其 Volume 栈
- 如何加快速度 用用户给出的区域缩小层级和材质查询范围。先确认物件，再扩展到共享 Shader，减少全工程扫描和无关场景取帧

### 5 工具输出过大与敏感信息暴露

- 出现的问题 一次返回 Unity 对象时，递归属性展开造成约 369 万字符的结果并被截断。完整日志和启动参数查询也曾输出过量内容，原始进程命令行中还包含访问令牌
- 为什么出现 没有在返回工具结果前限制对象形态、数量和敏感字段。Unity 的 Rect、Vector 等对象会带出派生属性，直接序列化可能持续展开
- 如何解决 查询返回字符串或必要标量。集合先按 Shader 或材质分组，再限制数量。详细证据写入指定文件，聊天只返回摘要和路径。启动身份只返回所需字段，令牌在输出前脱敏
- 如何加快速度 每次查询围绕一个待判断的问题设计结果。发现截断后收窄字段，不重复打印同一份大结果。读取日志使用本次运行的字节起点或明确时间范围

### 6 把测试工具失败、游戏失败与未知根因混在一起

- 出现的问题 多轮 Play 后 FMOD 初始化报告 ERR_MEMORY。重开 Editor 后曾出现寻路图缺失。帧调试器两次未抓到事件，其中连接的 profiler 为 -1，但改传 0 后仍然超时
- 为什么出现 已确认的是不同运行阶段的失败现象。资源不足的具体生命周期原因、冷启动寻路失败的原因和帧调试器无事件的原因尚未全部查明
- 如何解决 分别保留首次错误、运行身份、场景、已完成步骤和未完成步骤。热运行通过与冷启动失败分别记账。帧调试器超时后检查前置状态和支持性，实际截图、相机回读和材质验证可继续提供各自范围内的证据
- 如何加快速度 为取帧和加载设置有界等待。重复相同失败且没有新证据时停止该尝试，换用能回答当前问题的已支持观察手段。重启前先检查干净场景和隔离数据，重启后做与本次改动相称的验证

本例后续还遇到 Play 中挂起的脚本编译。Bridge 在 EditorApplication.isCompiling 为真时不领取请求，暂停请求过期，自由模式的退出准备也超时。通过原生 Unity 快捷键退出 Play 后，等待的编译完成，CLI 恢复。遇到这种状态先读编译诊断和原请求结果，确认操作是否执行。确需退出且已有授权时可用最少的原生 UI 操作，随后重新检查实例身份与 Edit 状态，不反复发送新请求或直接终止进程。

后续日志把寻路初始化失败追到 AssemblySearcher 调用 Assembly.GetName 时发生字符串转换异常，随后才出现无图和寻路协程错误。具体问题程序集尚未确认。这条调用链表明排查应从首次异常开始，不能仅根据后续无图消息推断场景缺少寻路资产。

### 7 验收表述比实际证据更宽

- 出现的问题 Shader 编译通过后仍可能绑定占位资源。一次拾取、击杀、撤离成功，也不能证明所有渲染恢复完成。测试器记录零错误时，原生日志仍可能有未计入的消息
- 为什么出现 把编译、绑定、画面和整条流程共用一个通过结论，忽略不同测试的观察范围
- 如何解决 分别记录源码或二进制来源、编译结果、绑定结果、实际画面和行为结果。人工采样动画、临时实例化特效、真实战斗取帧分别标明。失败记录保留，之后的成功不能抹掉首错
- 如何加快速度 为每个结论保留最少而充分的证据。最终报告直接引用这些证据及其边界，减少重复取证和返工

原始 Shader 的 Pass 数还须区分全部 SubShader 的总数与当前设备选择的 SubShader。本例 BokehDepthOfField 有两组各五个 Pass，原始对象合计十个，Unity 当前运行时 passCount 为五。验证预期应以实际后端和生效 SubShader 为准。

## 二 小弟的问题与协调方式

### 1 分析候选缺少排除性验证

- 出现的问题 执行者提出白斑可能来自雾效、拾取窗口可能提前关闭。雾效单因素对照没有消除白斑，真实拾取成功也没有支持窗口会阻断拾取的判断。后来实际找到的白斑来源是建造网格占位 Shader
- 为什么出现 根据症状相似性或静态调用顺序推断根因，尚未观察到目标对象的实际绘制或业务结果
- 如何解决 要求执行者返回对象、文件或调用位置、直接证据、可复现条件及最小反证。主协调者验证关键疑点，候选通过后才集成
- 如何加快速度 委派一个边界明确的调查问题，让执行者优先给出最短区分实验。已有反证推翻的候选停止继续展开

### 2 启动确认、执行和结果回传脱节

- 出现的问题 实例 2 的部分任务取得过实际回报，后续四个视觉子任务又出现管理器超时或回传未完成，无法据此确认模型是否完成了任务
- 为什么出现 超时可能位于投递、开始执行、工具运行或结果回传阶段。本会话没有足够证据给全部超时归因，不能把它们统一统计成代码错误
- 如何解决 对照原 request ID、task ID 和 session ID，区分已提交、确认开始、收到产物、已回报和主会话验收。结果未知时查原记录，遵守当前管理工具的重试契约
- 如何加快速度 首次回报包含已打开的目标和立即执行的步骤，最终回报包含具体产物与验证。把回传失败和任务实现失败分别统计，避免重复派发和重复整合

### 3 未明确共享 Editor 的使用权

- 出现的问题 多个会话围绕同一个 Unity 工程工作，导入、切场景、Play 和编译会相互影响。本会话发生过崩溃，但没有证据证明并发就是崩溃原因
- 为什么出现 文件隔离不能隔离 Editor、许可证、渲染设备和运行时资源。只读调查与会改变 Editor 状态的操作需要不同的协调方式
- 如何解决 由一个执行者负责共享 Editor 的状态变更，其他执行者处理可独立的只读调查或已授权的隔离工作区。交接时说明当前模式、允许的操作和产物位置
- 如何加快速度 并行查证互不依赖的资源来源、代码路径和候选范围，再由唯一集成人串行导入及验证。根据真正独立的工作量分工，减少同步和争用

### 4 执行提示没有给出最短取证路径

- 出现的问题 资源还原工作需要区分原始游戏编译数据、导出占位 Shader、已生成候选源码和运行时替换资源。仅给出症状容易让执行者重复全盘搜索，或引用了不对应的 PathID 和文件
- 为什么出现 输入缺少已知资源、来源容器、当前失败、已排除候选和明确交付物
- 如何解决 派发时给出目标、实际路径、已知依据、允许写入范围和验收方式。Shader 身份同时包含来源文件、PathID、名称和数据指纹。每个执行者直接完成自己的任务，递归权限按当前任务预算声明
- 如何加快速度 给出能立即执行的首个查询和预期产物，让执行者从最近的有效证据继续。复用已核验资源，避免不同会话重复提取和编译同一份数据

### 5 没有按错误类别评价执行者

- 出现的问题 用户问小弟是否经常出错时，服务连接失败、回传超时、分析被推翻和未验收结果容易被合成一个模糊的错误率
- 为什么出现 缺少任务总数、完成数和错误分类，也混淆了执行端前端、模型后端与具体任务表现
- 如何解决 有记录时分别统计投递失败、工具错误、超时、被反证的分析、集成后回归和通过验收的任务。缺少分母时直接说明可确认的个案和未知项
- 如何加快速度 用这些分类调整委派内容。分析偏差多时缩小问题并要求直接证据，回传问题多时先修链路，独立性不足时由主会话串行完成

## 后续任务的最小交接内容

每次交接只带当前执行者需要的内容。

- 当前目标与具体问题位置
- 准确的实例、会话、工程与运行身份
- 已确认事实、已排除候选和仍待验证的假设
- 可写范围、共享资源使用权和递归预算
- 本次产物、最短验收步骤与回传方式

## 本会话的验证边界

- 已实测修复包括地堡建造网格白斑、弹着烟雾、死亡闪光和准星 Sprite 留边。后续 FadeUI 恢复后拍到了覆盖黑幕与局部圆形转场
- 后处理回读确认 Bloom、ACES 和景深进入实际相机的 Volume 栈。这只证明对应效果正在运行，原版视觉等价仍需对照
- 用户把紫色材质位置缩小到新手教学关卡中段走廊地面，后续反馈紫色现象已消失。具体地面物件的根因尚未单独证实，不能用该反馈倒推某枚 Shader 就是唯一原因
- 后续血液黑块定位到 HitFx_Blood 的 BloodSplash 材质使用占位 SodaCutout。接回原版编译 Shader 后，固定机位和粒子阶段取样中的黑色方片消失。该证据覆盖预制体渲染，实际战斗触发未在这一轮重跑
- 原版 Shader 的可编辑源码恢复、原编译数据加载、变体编译和实际视觉分别有各自证据。原版依赖或数据缺失时保留缺口
- 本例证据位于用户指定的 E:/AAAA学习资料/YaKeFu/Evidence/SourceVerification。122-visual.log 记录了本轮视觉探针、两次帧调试器超时、原存档校验与测试夹具清理。该运行不是完整游戏流程通过记录
