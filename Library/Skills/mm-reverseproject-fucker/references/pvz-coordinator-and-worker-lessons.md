# PVZ 会话经验 协调者与子执行者

供主 skill 在处理原程序逆向 源码回填 Unity 联调或取消还原转为资源工程时按需读取。本文件是 PVZ 会话的独立贡献，skill 入口及跨会话归并由创建该 skill 的会话维护。

依据为本会话可见的任务演变、工具回报、候选交付和失败修复。本轮不读取其他会话、不重跑逆向或 Unity 验证，也不保证历史证据文件今天仍在原路径。原因分析限于工程机制，不推断执行者动机；未发生的问题不写成已发生事故。

## 一 协调者的问题

| 出现了什么问题 | 为什么出现 | 如何解决 | 如何加快速度 |
| --- | --- | --- | --- |
| 先推进了可玩重建，后来用户明确要求指定 Replanted.exe 的原代码与原体验，工作主线需要重置 | 可玩仿制、依据原资源重写、从原机码恢复方法、完整原版运行没有在早期形成清楚的交付边界 | 指定唯一参考程序与版本，分别定义源码来源和运行验收。需求明确后重新安排主线，并明确已有试玩属于哪种交付，不能沿用旧完成口径 | 动手前先核安装包是否含作者源码、实际脚本后端及原启动入口，尽早暴露决定路线的前置缺口 |
| 累计恢复188个游戏方法、58份源文件和一个库getter，仍未跑通完整原关卡 | 短访问器、标量判定和随机数容易独立验证，方法数与断言数增长没有自然补齐 Bootstrap、状态机、注入、存档和 Board 初始化 | 以用户可观察的完整链作为里程碑。原始提取覆盖、方法等价、实际程序集执行、完整场景运行分别报告，不把大量局部 PASS 计成整游戏进度 | 先沿一个真实入口列出阻断执行的必要节点，优先关闭最短运行链；短方法可配套恢复，但不能占据全部关键路径 |
| 大量候选文本、资源路径命中率和结构壳统计容易形成错误预期 | 提取成功、路径存在、类型齐全、方法有非空 IL 都容易计数，却不能证明业务实现正确 | 明确“作者原文件未取得”。本例早期99%是路径命中口径，77.5%是旧短IL比例，都不能当作游戏还原率。自动反编译候选始终与已核验源码分开 | 在全量流水线前抽查有确定分支和类型的代表方法；先证明工具能回答语义问题，再决定是否扩大产出 |
| 在候选最终冻结前做过 staging 编译，随后候选补显式构造器、事实文件变化，又需要重绑证据和编译 | 分析中产物与可交接产物的状态不够明确，完整文件拷贝还携带旧基线及换行变化 | 交接声明候选是否冻结，绑定来源身份、基线、最小差异、候选哈希及实际验证范围。集成者只接已声明可集成的版本；必要的格式转换另记映射 | 先做最小格式与接口探测，冻结后再执行正式编译。变化只重验受影响部分，避免每次文本更新都重跑整套工具 |
| 长命令的结果、实际日志与后续操作脱节 | Unity CLI 包装器直接写 Console，shell重定向得到过零字节日志；多行 Python 的引号错误后，依赖调用又指向未生成的脚本 | 记录进程退出码、运行会话ID及原始 stdout，检查日志非空。生成文件成功并确认文件存在后再调用它；已失败的准备步骤不能继续触发依赖操作 | 复杂命令写入合规临时脚本或正式可复用工具，减少多层引号。工具输出只返回必要字段和路径，不打印整份方法图或递归目录 |
| 50个资源的同步清理超过服务5秒等待，但主线程实际已处理完前50个 | 调用方等待结束与 Editor 中的副作用完成不是同一事件；把超时直接等同失败会造成重复修改 | 先查原请求对应的持久进度，确认 Cursor=50后才从后续位置继续。将长操作改为 Editor update 分批执行，记录原子更新的游标、结果和首错 | 首次调用只处理小范围或启动后台作业并立即返回；由任务ID及持久状态查询结果，避免在同步工具调用内塞入整批工作 |
| 重复安装、重编译和版本漂移可能污染正在验证的 Editor | 安装第一次超时时结果未知，稍后才确认过期；新构造器加入后，同样的业务方法也可能获得不同metadata token和raw IL哈希 | 复用准确工程、版本、PID与现有连接。未知写入结果先查原请求，取得明确失败并修复原因后再重试。程序集变化后重新绑定运行证据，不能沿用旧SHA冒充当前运行 | 主协调者独占共享Editor状态变更，执行者并行查原字节、元数据和候选；检查实际变更的程序集和方法，不重复启动多个Editor或重提取全部原数据 |
| 转资源工程时把整个 Assets/Editor 归档，Spine随后重新生成了显示设置，最终目录检查因此失败 | 依据目录名把文件全当逻辑，没有细分自定义工具代码和SDK资源设置 | 恢复清理前 SpineSettings.asset 及其meta、目录meta，并保留新生成文件作为记录。检查代码后缀及明确资源白名单，不能用“Editor目录必须不存在”替代无游戏代码条件 | 删除前按用途建立依赖清单，保留渲染SDK和资源设置。先在副本或归档下检查拟移除对象，再通过Unity API移除组件、事件和资源引用，最后移走代码 |

协调者应承担路线、集成和最终口径的责任。即使候选来自子执行者，也不能把集成后的范围扩大表述归责给子执行者。

## 二 子执行者产物中的错误与交付问题

这里区分可归到产物的错误、执行工具的缺陷和环境限制。交付前发现并拒绝的问题不等于错误代码已发布；没有任务总数和统一分母时，不计算“小弟错误率”。

| 出现了什么问题 | 为什么出现 | 如何解决 | 如何加快速度 |
| --- | --- | --- | --- |
| 两份候选源码把原CRLF整体改成LF，形成无关的整文件字节变化 | 用文本读写生成整类候选时没有保留原换行和BOM | 冻结候选不再改动，在staging明确恢复原格式。分别绑定原文件、冻结候选、格式处理后文件和应用备份的哈希，按白名单核对语义差异 | 执行者直接交最小修改块，或在首次写入时保留原编码格式。先检查一份候选，避免全批生成后再处理格式噪声 |
| 初始化证据采集器首次漏掉OBJECT类型码0x1C，冻结自检失败 | 元数据类型解析覆盖不足，工具尚未支持实际输入类型 | 保留首次错误，补齐解析后完整重生成和重跑，再冻结产物。遇到未知类型应报错，不能默认成另一类型继续输出 | 在跑全量前，用任务实际涉及的字段类型做小样本验证；将未支持类型单独列出，减少无效的大批导出 |
| 用Cecil重写仅改单个getter的DLL，却产生非目标token重排和特性顺序变化，严格检查拒绝该产物 | 选择了会重建整个元数据布局的写入器，本次要求却是控制非目标差异；这不等于已证明每次Cecil重写都会损坏Prefab | 首轮产物和失败保留。本例在确认无签名、已有零padding足够且原表位置可验证后，采用受控PE字节补丁；非目标IL、元数据、token和meta仍按原门禁检查，并实际验证场景MonoScript身份 | 先在原DLL副本上做一次最小写入与往返差异检查，尽早判断写入器是否满足范围。不要等多个方法完成后才检查元数据副作用；条件不成立时停止该补丁路线 |
| 构造器的事件依赖起初尚未闭合，字段测试容易被理解为整个初始化已经通过 | 只看到接口上的 += 或“没有直接调用handler”，不能说明具体事件add没有同步副作用 | 追到实际 PlatformService.add_MainUserIdentified，确认已有主用户时先Invoke再Combine。候选保留原订阅语句；真实add、OnPlatformReady和加载链未恢复时，只认可已实测的默认字段和空档案路径 | 优先追查可能同步回调或重入的外部调用，用能区分未就绪、已就绪和同步回调的场景取证，再扩展正常构造样本 |
| 自动工具产物看似完整源码，实际包含占位IL、错误分支和被截断的静态初始化 | Cpp2IL某输出器只产ldnull/throw，新候选又有Coin无符号/零标志语义错误；Ghidra曾因GC写屏障跳板的控制流识别而漏掉静态构造后半段。这些是已识别的工具缺陷，不应算成模型凭空写错 | 逐项核对原方法身份、字节、分支、元数据和调用目标。静态初值与构造顺序要追到完整原指令；保留BeforeFieldInit等真实契约，未验证候选不批量导入 | 先选包含边界比较、初始化和一次外部调用的代表方法做差分。函数长度、首段unwind或提取成功数只能辅助定位，不能替代完整方法范围 |
| 在普通.NET运行验证器时，真实Unity ECall不可用；引擎脚本首次通过GetAssemblies/GetName定位程序集又触发Mono Unicode CodeBase错误 | 计算逻辑验证与引擎对象验证使用不同运行环境，枚举所有程序集还增加了不必要的异常面 | .NET中明确记Unavailable和非零退出，本例对应部分报告保持PARTIAL/exit2；之后在真实Unity补测。已知类型通过typeof定位实际程序集，不移除cctor、不换假Unity类型让断言通过 | 把纯计算差分与引擎依赖分组，直接加载目标实际程序集。补测只覆盖明确缺失的层级，保留旧环境不可用的记录，不把它算成执行者算法错误 |
| 新初始化接入后，已审方法中7个raw IL哈希变化，不能继续使用“字节相同”的结论 | 元数据token重编号也会改变IL字节，raw SHA只能证明字节身份，不能独立判断实现是否改变 | 同时记录旧新raw SHA，解析字段和方法引用后比较完整IL语义。本例8个目标方法的签名、局部变量、栈、分支和解析引用一致，不能靠删除常量或分支来制造一致 | 先定位差异是RVA、token、引用还是实际指令变化；只对目标方法做严格规范化比对，避免不必要的回滚、全库逆向和重复取证 |

共享原生地址同样不能直接决定业务命名。本例0x60F880对应多个无操作方法，Ghidra显示的AudioSourceWrapper.SetPitch不能证明UpdateGame在那里执行调音高；原vtable和调用消费没有确认前，应保留地址身份及未知项。这是防止工具标签被误当作执行者结论的边界。

## 三 下一次如何更快完成同类任务

1. 先确定最终交付是资源工程、重写试玩还是原逻辑还原，明确可证明的源码来源。用户改目标时，停止旧目标的新增工作，更新权威状态及历史记录的适用范围。
2. 从真实启动入口选择最小贯通目标，先处理会阻断它的状态机、注入、数据和回调。给前置探测与首个贯通目标分配与任务相称的时间预算，到期依据首错和缺口重估，不用固定方法配额代替目标。
3. 仅委派能独立推进的调查或局部候选。输入带准确来源身份、当前基线、已排除假设、可写范围和明确验收；共享Editor由一个集成人操作，避免重复调查同一问题。
4. 每个交付标明静态候选、可编译、原指令差分、实际程序集执行或真实场景行为中的实际层级。列清拦截调用、替身、未执行分支及首错，不只回报PASS数。
5. 冻结后最小集成。源码哈希用于确认未变，解析后的引用和控制流用于解释token变化，真实Unity用于验证引擎依赖；新改动或明确未决项才扩大复验。
6. 长任务通过持久游标和有界批次交付进度。工具超时、结果回传失败、编译失败和业务结果错误分别记录，先确认原任务状态再决定重试。
7. 资源清理先保留需要的SDK、设置及meta，再移除游戏组件和事件引用，最后归档源码。对保留资产检查GUID及不可变文件哈希，对修改的Prefab/场景检查目标组件及Missing Script，避免只统计删了多少文件。

## 四 本会话的证据边界

- 原作者C#/C++文件未取得。回填188个游戏方法及一个状态机库getter时，完整原版关卡仍未跑通，后来用户取消了原逻辑恢复。
- 本会话报告过Common/Ground 4537项真实Unity方法差分、档案7例2181断言、Mode与场景脚本身份14例通过。这些分别证明各自范围，不能合并成原版完整体验通过。
- 最终目标改为资源工程。清理报告记载移出840份游戏/工具源码、49个DLL、818份依赖游戏类型的数据资产，保留560个Prefab与7个资源场景；真实Unity Missing Script为0。该资源交付不能反向证明先前游戏恢复完成。
- 历史追证可按文件名查找：`profile_initialization_recovery/integration_review.json`、`framework_getter_batch/byte_patch/semantic_diff.json`、`engine_runtime_review.json`、`asset_only_cleanup/cleanup_report.json`、`finalization_first_guard_error.json`。它们在会话当时位于PVZ工作区的`UnPack`下；本轮没有重新确认其磁盘存在性。
- 这里保留能够改变后续决策的案例，不要求其他项目沿用该项目的版本、地址、方法数量、批次大小、工具选择或目录结构。
