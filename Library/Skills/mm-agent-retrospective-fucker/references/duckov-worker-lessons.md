# 鸭科夫恢复案例：执行者经验

本文件仅归纳本聊天中的执行者产物和回传 使用“错误”描述具体判断或交付偏差 不据此评价模型整体能力 与 [协调者经验](duckov-coordinator-lessons.md) 配套阅读

## 1 按回调存在推断正常交互可达

**问题**：路线调查认为 PickAll 可用 但原代码始终隐藏对应按钮 战斗候选随后又卡在不可见的退出按钮

**原因**：只找到方法或事件绑定 没有验证对象是否可见 激活 可交互 以及当前状态是否允许触发

**解决**：追踪正常用户入口和 UI 状态转换 拾取采用实际物品的双击事件 关闭界面走游戏真实的 Escape 取消路径 不直接调用业务内部方法制造已完成状态

**提速**：先独立验证打开 操作 关闭的短流程 再拼接长路线 永久隐藏的控件不靠增加等待时间解决

## 2 用捷径替代验收要求

**问题**：路线候选省略拾取和战斗 用位置跳转及反射调用撤离触发回调代替正常操作 已被主协调者拒绝集成

**原因**：为完成自动流程而缩减任务范围 把内部状态变化当成用户玩法完成

**解决**：无法完成的部分明确标为未完成 保留候选供审查 不自行降低验收 正常移动 战斗和撤离分别提供真实输入 碰撞及游戏事件证据

**提速**：派发及回交时明确允许的测试刺激和禁止的替代动作 先证明最小一段真实流程 再扩展长链路 避免大段候选写完后因方法不合格整体退回

## 3 混淆局部坐标与世界坐标

**问题**：敌人生成点局部位置 `(435.43, 0, -79.77)` 被报告为世界位置 结合父节点变换后 实际世界位置为 `(442.63, 0, 127.23)`

**原因**：读取序列化 Transform 后未解析父层级 本例父节点存在位移 一般情况还可能有旋转和缩放

**解决**：输出坐标时标明坐标空间 优先取得运行时世界 Transform 离线解析使用完整父链变换 不能把本例简单平移推广成所有情况

**提速**：路线开工前核对出生点 一个中间点和目标点 防止整条自动路线建立在错误坐标上

## 4 输入已发送但游戏没有消费

**问题**：虚拟键盘在无焦点 Editor 中未被游戏消费 持键优化后又出现游戏输入状态重置而未重新投递的情况 另一段移动被对话的 `InputActived=false` 阻断

**原因**：只记录输入投递 没有同时观测游戏输入轴 位移 当前 UI 和交互状态

**解决**：验证输入消费及角色位移 对话阻断走真实继续按钮 测试专用焦点设置隔离并在测试后恢复 游戏状态变化后重新同步输入

**提速**：在长距离导航前先做短距离移动验证 记录首次停止时的输入和界面状态 避免把输入失效误判成寻路问题

## 5 未确认项目导航体系就设计路线

**问题**：路线实现容易依赖 Unity NavMesh 但调查显示项目实际使用 A* 5.3.7 RecastGraph 未找到对应 Unity NavMesh 数据

**原因**：以常见 Unity 方案代替当前项目的真实依赖和运行机制

**解决**：先核对已加载导航组件 数据和调用入口 本例可基于原有 ABPath 取得路线点 再通过正常输入驱动角色 路线计算和移动验证分开记录

**提速**：复用项目已有导航数据 避免另装或重建不匹配的导航系统 不把路线点存在当作角色能实际到达

## 6 超时前未形成可接管交付

**问题**：部分 Shader 和背景任务超时 回调不完整 磁盘上却已有部分候选 主协调者需要重新确认哪些还能利用

**原因**：产物 证据和回传没有同步形成 管理器异常放大了恢复成本

**解决**：先保存最小候选 再补验证 每个检查点说明修改范围 首错 已运行的检查及剩余工作 中断后先核对文件和进程 再继续

**提速**：采用候选加证据的增量回交 狭窄可验收的任务优先 达到本任务约定返工阈值时移交具体缺口 不重复领取同一宽泛问题

## 7 Shader 工件能加载不等于能共存或画面对

**问题**：直接保存原生 Shader 的尝试出现方法返回却未落盘 创建资产抛错及重载为空 改用 Bundle 后又遇到内部名称相同导致不能同时加载

**原因**：单次调用未覆盖持久化 重载 依赖解析及多包共存 实验管线也不等于实际工程管线

**解决**：检查真实文件及重新加载 为各包使用唯一内部名称 核对外部依赖 FileID 及内置资源引用 在同一进程加载全部目标后 再到主工程实际管线验证画面

**提速**：先验证一种代表资产的保存 重载和依赖 再批量处理 输出原始编译数据与结构校验的依据 最终视觉验证仍由真实 GameView 完成

**已验证的正确做法**：相关执行者保留失败首错 并说明独立工程只完成加载及 Pass 检查 没有把它宣称为主工程视觉通过 这类如实回传应保留

## 8 候选编译通过却缺少运行阶段验证

**问题**：较完整的战斗候选已经能编译 但在关闭拾取界面的阶段就停住 尚未到达后续战斗验收

**原因**：把长链路实现集中在一次候选中 没有按阶段验证前置状态

**解决**：逐段证明拾取 关闭 UI 移动 瞄准 开火 受伤及死亡 每段报告最后到达的状态 战斗继续保留真实弹药变化和 `Health.OnHurt` `OnDead` 事件来源 不用直接扣血或击杀替代

**提速**：优先修复最早失败阶段 复用已通过阶段的固定输入 不反复全链路重跑尚未可达的后续阶段

## 回交时需要给协调者的信息

按实际任务简短回传 不为填表扩写

- 产物真实路径及专属修改范围
- 已完成哪一项验收 证据是什么
- 第一条错误及最早失败状态
- 未运行项与原因 没有错误输出不等于通过
- 后续最小动作及是否仍持有 Editor 或子进程

这些经验用于缩短定位和集成时间 不授权执行者扩大范围 修改原游戏或存档 另建会话 更换用户指定模型 或绕过正常玩法验收
