## 3 注释与重构规范

- 默认不新增注释 优先通过准确命名和清晰结构表达意图
- 注释必须补充无法从命名 签名和局部实现直接看出的信息 禁止翻译名称或复述代码
- 按需说明业务约束 单位与坐标系 调用前置条件 生命周期与资源归属 非显然副作用 算法选择原因
- 字段 属性和函数不因访问级别或代码长度强制注释 局部变量默认不注释
- 需要说明字段或函数契约时使用 XML summary 字段内容一行 函数内容换行 算法选择原因使用 //
- 改代码保留原注释 错误则原地修正 未明确要求不批量清理既有注释
- 注释言简意赅 禁用句号逗号冒号 禁止逐行注释和无意义版本标签

注释尽量一行完成 言简意赅 输入什么 做了什么 输出什么
注释禁用句号逗号冒号 可用空格替代 改代码保留原注释 错误则原地改 复杂函数可内注但禁止逐行
变量必须三线注释 属性无需注释 函数三线注释换行 算法抉择处加双线注释 `// 内容`
数组后缀 List 字典 Dict HashSet 后缀 HashList

- 重构时注释不要 `xxx(无问题版)` 这类废话 需要时直接重构

## 4 命名与访问修饰

- 变量 属性 方法必须标注 public private protected 等 特性与变量分行
- 变量永不加 `_` 前缀 脚本超 200 行加 region region 不标记字段和属性
- 函数内临时变量：基础值类型写出类型 如 `int a = FunctionReturnInt()`；引用类型与结构体和枚举可用 var 变量名帕斯卡；如果是枚举则前加小写 e 如 `ePathEnum`



## 5 函数 状态与容错

- 有 Unity 组件 → `InitComponents` 无 → `Init`
- 仅由唯一生命周期或唯一初始化入口调用一次 非系统层建议放 Start 或显式获取对象后调用
- 禁止在属性访问器 Show Refresh Set 等业务函数中重复调用
- 反复重建或重新布局不得叫初始化 用 `RefreshXXXX`
- 纯工具无状态可用静态方法 游戏实例函数尽量不存静态状态 避免内存泄漏
- 无额外提醒时 不额外增加判空 边界 数值兜底

## 9 工程纪律

- Fail fast：不吞异常 不用无依据 fallback 掩盖问题 错误尽快暴露并带足够上下文 只有需求明确恢复策略才实现恢复
- 歧义处理：有实质歧义或矛盾必须指出 会实质改变结果 授权范围或不可逆后果时先询问 已记录默认值和任务内常规实现选择可直接执行
- 不伪造 PASS：不吞异常 不放宽断言 不静默切换工具链让检查通过 保留首错 真实范围及未运行/不可用原因
- 默认单 Agent 在当前工作区完成任务 不主动增加协作层级
- 主会话 独立子执行者与联调会话默认各可并发使用最多 3 个原生 Subagent 这是可用额度 可以不开 不要求凑满 显式更低预算和宿主硬上限仍生效 Session 与联调树额度不占用原生 Subagent 额度
- 每个原生 Subagent 必须有立即可执行的具体任务 明确输入 可写范围 产物和验收 不得为占位开启或让其空等 原生 Subagent 是叶子 禁止递归创建 Subagent 或通过 Session 与跨实例转派绕过 派发时明确其 subagent_max=0 session_max=0 cross_agent_max=0 且不得继续委派
- 自动判断：只有存在可独立推进的工作单元 职责与交付物清晰 且预计收益超过启动 上下文同步和整合成本时 才启用协作 不以文件数 代码量或任务耗时单独作为依据
- 默认不启用：普通问答 小范围修改 单一路径排错 强顺序依赖 或需要频繁共同修改同一批文件时 由当前 Agent 连续完成

- 子 Agent：符合上述条件时 主动调用可用的子 Agent 工具 分派独立调查 分析或局部实现 无需逐次询问 主 Agent 保留关键路径工作并负责整合 不重复执行已分派的任务
- 同一协调者负责的跨实例执行会话有 3 个及以上时 可在现有额度内按需开启原生 Subagent 按会话或模块分担对接 进度跟进和结果预审 每个子代理须有明确对接对象与交付物 协调者负责最终验收和整合
- worktree：多个 Agent 并行修改同一仓库时 每个写入者使用独立 worktree 和独立分支 优先复用合适的已有 worktree 新建与检出位置遵守第 13 条 无合适隔离工作区且用户未明确授权新建时改为串行执行 只读调查无需创建
- 多会话：仅在多个模块需要跨多轮持续独立推进 且用户已明确授权创建或协调相关会话时使用 明确各会话的模块归属 接口约定和集成负责人 不因任务较大自动新建聊天

- 协作交付：分派时明确目标 范围 依赖和验收方式 执行者只提交自己负责的改动 由单一集成负责人串行合并并重新验证 集成修复单独提交
- 共享资源：worktree 只隔离工作区文件 不隔离外部服务 端口 数据库或编辑器实例 共享资源存在冲突时明确独占归属或串行操作
- 执行边界：仅调用当前环境实际提供且允许使用的工具 不以规则替代工具权限 工具不可用时继续可独立完成的工作并说明限制
- 沟通：启用协作时用一句话说明分工与原因 未启用时无需额外汇报判断过程



## 10 Git 提交规范

- 每个 commit 对应一个具体 可独立解释和审查的修改目的
- 粒度以具体能力 具体问题或具体重构为单位 同一需求下的多个独立目的分别提交
- 能独立成立的重命名 目录整理 格式调整和顺手修复分别提交
- 同一目的所必需的代码 资源 配置 `.meta` 和配套文档一起提交 独立的文档整理使用 `docs` 提交
- 按依赖顺序组织提交 确保每个提交的编译依赖和资源引用完整
- 提交前检查实际 `diff` 简要列出每个拟提交的目的 范围和标题 再按分组执行
- 每次提交前检查暂存区 `diff` 确认其中所有修改都服务于该提交目的 同一文件包含多个独立目的时按修改块拆分
- 只暂存本任务增量 混有用户改动的文件按块暂存 开始 提交前 结束都检查 `git status`
- Commit Message 用 `type: description` 格式 type 取 `feat` `fix` `refactor` `perf` `docs` `test` `style` `chore`
- description 用中文描述 专有名词可保留英文 标题写明具体修改对象和行为变化
- 涉及公共接口 程序集边界 生命周期或确定性行为变化时补充正文 说明修改原因 关键变化和受影响的调用方式
- 提交完成后列出每个 commit 的哈希 标题和实际范围
- 未经明确要求禁止 `git reset --hard` `git clean -fd` 破坏性 checkout 或批量删除 移动/删除前核实准确目标 之后检查引用与链接

## 13 文件系统 临时文件与环境变量
